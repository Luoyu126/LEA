# x86 寻址模式时序实验方案

Oct 27, 2026 · @Yunyi

## 背景与研究问题

**研究问题**：功能相同或等价的 x86 指令，仅因寻址模式（addressing mode）不同，执行时间是否不同？本方案用 4 个 microbenchmark 实验回答它，预计 3–6 小时完成。

**作业要求**：2 人一组，3–6 小时，鼓励用 AI/LLM 辅助（避免高 token 成本的大模型）。最后 5 分钟汇报，需包含：如何用 AI 调研、workload/microbenchmark、alternate hypotheses。

**核心思路**：

- `LEA`（Load Effective Address）按寻址语法算出地址，但不访问内存，只把地址值写入寄存器。因此它没有 cache 干扰，可以干净地测出寻址形式本身对时间的影响。
- 文献（Intel 优化手册、uops.info、Agner Fog）报告：在部分 Intel 核心（如 Skylake）上，2 分量 LEA 约 1 cycle，3 分量（base+index+disp）或特殊 base（RBP/R13）+index 约 3 cycles，且只能走一个端口。
- 但现代 Intel 上 LEA 在 ALU 端口执行，真正访存的地址由 AGU 计算，两者是不同硬件。所以“LEA 能否代表访存寻址开销”本身是一个需要检验的假设（实验 4）。

**汇报主线**：LEA 证明寻址形式会影响时间；load 实验说明访存寻址有另一套规律；两者合起来回答题目。

**给新 Code 会话的说明**：本文档是完整执行规格。新会话应先完成第 0 步（确认 CPU 与 perf 权限），再按实验 1→3→4→2 的优先级执行，所有结果写入 `results.csv`。

## 0. 环境准备与测量框架（约 1h）

harness 通过 sanity check（`add rax,1` 依赖链测出约 1.0 cycle）之前，不跑任何正式实验。

**确认机器**

1. `lscpu` 记录 CPU 型号与微架构（Intel/AMD、代际）。混合架构（Alder Lake 及以后）需列出 P-core 与 E-core 编号。
2. 确认 Linux 与 `perf` 可用：`cat /proc/sys/kernel/perf_event_paranoid` ≤ 2，或有 sudo。
3. 确认有汇编器（GNU `as` 或 `nasm`）、gcc、Python 3（含 matplotlib）。
4. 到 [uops.info](https://uops.info/table.html) 查该微架构的 LEA/MOV 参考值，作为对照基准。

**Harness 设计**

- Python 脚本根据参数生成汇编 kernel：一个循环，循环体展开 N=200 条目标指令，循环迭代约 10⁶ 次。
- 寄存器初始化在循环外完成（如 `rcx=0`、指针指向自身的内存）。
- 用 `perf stat -e cycles,instructions -x,` 测 core cycles；不用 TSC，避免 turbo 和频率变化的影响。
- `taskset -c <core>` 绑到固定核心；混合架构 P-core、E-core 分开测。
- 每个 kernel 运行 7 次取中位数，同时记录最小值和最大值。
- 结果 = (kernel cycles − 空循环 cycles) ÷ (N × 迭代次数)，单位 cycles/instruction。

**Sanity check**

- `add rax,1` 依赖链 → 约 1.0 cycle（延迟）
- `imul rax,rax` 依赖链 → 约 3.0 cycles（多数现代核心）
- 4 条独立的 `add` 链 → 约 0.25–0.33 cycle（吞吐）

以上任一偏离超过 10%，先排查 harness（展开数、迭代数、绑核、频率）。

**统一输出格式**：`results.csv`，列为 experiment, kernel, form, path, metric (latency/throughput), cycles\_median, cycles\_min, cycles\_max, core。

### 执行环境：Windows 电脑（待执行会话确定）

用户的电脑是 Windows。执行会话开始时，先在以下两条路线中选定一条，再开始实验。

|  | WSL2 | 原生 Windows |
| --- | --- | --- |
| 编译工具 | gcc + GNU as | MSYS2/MinGW gcc（支持 GNU 内联汇编），或 MSVC + 独立 .asm（MSVC x64 不支持内联汇编） |
| 计时 | `perf stat -e cycles`（若可用），否则 rdtsc | rdtsc（`__rdtsc()` 或内联 `rdtsc`） |
| 硬件计数器 / 端口统计 | 取决于 WSL 是否暴露 PMU，常常不可用 | 需 Intel VTune / AMD uProf 等驱动级工具，作业中可不做 |
| 绑核 | `taskset`（绑的是虚拟 CPU） | `SetThreadAffinityMask` 或 `start /affinity`，可绑到物理核心 |
| 噪声 | VM 带来额外噪声 | 较小，但需关闭后台程序 |

**第一步检查**：

- [ ] 记录 CPU 型号（任务管理器 → 性能 → CPU），判断是否为混合架构（Intel 12 代及以后有 P-core/E-core）
- [ ] 若走 WSL：运行 `perf stat -e cycles,instructions true`，看 cycles 是否可用

**rdtsc 校准法**（perf 不可用时的统一方案）：

1. rdtsc 测的是固定频率参考时钟，不是 core cycles。
2. 每次测量同时跑 `add rax,1` 依赖链（已知 1 cycle/条），换算：目标 cycles/条 = 目标 TSC/条 ÷ add 链 TSC/条。
3. 前提是频率稳定：Windows 电源计划把“最大处理器状态”设为 99%（通常可关闭 turbo），接通电源，关闭后台程序，提高进程优先级。
4. 后果：实验 2 只报吞吐，不做端口分布；汇报时作为方法论局限说明。

**原生 Windows 注意**：Win64 调用约定中 rbx、rbp、rdi、rsi、r12–r15 为 callee-saved，kernel 使用前必须保存/恢复（与 Linux 不同，rdi/rsi 也要保存）。

## 实验 1：LEA 延迟 sweep（主实验，约 1h）

**假设**：在 Skylake 一类核心上，3 分量形式和 RBP/R13+index 形式约 3 cycles，其余约 1 cycle；较新的核心差距可能缩小或消失。

**方法**：每条 LEA 的输出是下一条的输入（依赖链）。base 路径与 index 路径分开测：把链寄存器 rax 放在 base 位置测 base→dst，放在 index 位置测 index→dst。另一个寄存器 rcx/rbx 在循环外初始化，保持不变。

| 形式 | base→dst 路径 | index→dst 路径 |
| --- | --- | --- |
| base | `lea rax,[rax]` | — |
| base+disp8 | `lea rax,[rax+8]` | — |
| base+index | `lea rax,[rax+rcx]` | `lea rax,[rcx+rax]` |
| base+index×4 | `lea rax,[rax+rcx*4]` | `lea rax,[rcx+rax*4]` |
| index×4+disp（无 base） | — | `lea rax,[rax*4+8]` |
| base+index+disp | `lea rax,[rax+rcx+8]` | `lea rax,[rcx+rax+8]` |
| base+index×4+disp | `lea rax,[rax+rcx*4+8]` | `lea rax,[rcx+rax*4+8]` |
| RBP 作 base +index | — | `lea rax,[rbp+rax]` |
| R13 作 base +index | — | `lea rax,[r13+rax]` |
| 32 位目标 | `lea eax,[rax+rcx+8]` | — |

**注意**：

- index 路径链中 rax 会指数增长甚至溢出；LEA 不访存，溢出不会出错，不影响计时。
- RIP-relative（`[rip+x]`）没有寄存器输入，无法构成延迟链，只在实验 2 测吞吐。
- 用 RBP/R13 前确保 harness 保存并恢复 callee-saved 寄存器。

**输出**：柱状图，x 轴为形式，y 轴为 cycles，base 路径与 index 路径分组；旁边标注 uops.info 参考值。

## 实验 2：LEA 吞吐与端口（约 1h，时间紧可简化）

**假设**：slow LEA 只能派发到一个端口（Skylake 上为 port 1），吞吐明显低于简单 LEA；这是“不同形式使用不同执行资源”的直接证据。

**方法**：

- 对实验 1 的每种形式，用 8 条互不依赖的链轮流执行（目标寄存器 rax, rbx, rdx, rsi, rdi, r8, r9, r10 轮换，源寄存器固定），测 cycles/instruction，即倒数吞吐。
- 额外加入 RIP-relative：`lea rax,[rip+label]`。
- Intel 上同时采集端口事件：`uops_dispatched.port_0` 至 `port_7`（具体名称用 `perf list | grep -i port` 确认，不同代际不同）。AMD 用 `perf list` 查对应的 dispatch 事件，查不到就只报吞吐。

**输出**：吞吐柱状图 + 每种形式的端口分布表（各端口 uop 数 ÷ 指令数）。

**简化版**：只测 4 种代表形式：`[rax+rcx]`、`[rax+rcx*4]`、`[rax+rcx+8]`、`[rax+rcx*4+8]`。

## 实验 3：等价编码对照（约 1h，紧扣题目中的 “equivalent”）

**假设**：如果时间差来自寻址“形式”，那么计算结果相同、只有编码不同的指令，耗时应取决于形式而非编码长度；反之则说明是前端/编码因素。

每组内的指令计算结果完全相同，均测依赖链延迟（必要时加测吞吐）：

| 组 | 对照 | 检验什么 |
| --- | --- | --- |
| A | `lea rax,[rax+rax]` vs `lea rax,[rax*2]` | 后者无 base，编码必带 disp32：形式更简单但编码更长 |
| B | `[rax+rcx]` 的 disp 分别编码为无 disp / disp8=0 / disp32=0 | 纯编码长度的影响；用 `.byte` 手写机器码强制编码，并用 `objdump -d` 核对 |
| C | `lea rax,[rbx+rax]` vs `[r13+rax]` vs `[rsp+...]` 类形式 | 特殊寄存器带来的 disp8/SIB 编码差异 |
| D | `lea rax,[rax*4]` vs `shl rax,2`；`lea rax,[rax+rcx]` vs `add rax,rcx` | LEA 与等价算术指令 |
| E | `lea rax,[rax+rcx+8]` vs `lea rax,[rax+rcx]` + `add rax,8` | 一条 slow LEA 与拆成两条快指令哪个更快 |

**组 E 的延伸**：写一个小函数，如 `long f(long a,long b){return a+b*4+8;}`，用 `gcc -O2 -march=native -S` 和 `-march=skylake` 编译，看编译器是否把 3 分量 LEA 拆开。这是汇报中“指令更多反而更快”的展示点。

**注意**：组 C 中 RSP 改动会破坏栈，用 `[rsp+rax]` 时链寄存器放在 index 位置，不修改 rsp 本身。

## 实验 4：真正访存的寻址（pointer chasing，约 0.5–1h）

**假设**：Intel 上 load-use 延迟对简单寻址 `[base+disp]`（disp 较小）约 4 cycles，带 index 约 5 cycles；这一差异模式与 LEA 不同，说明 LEA 不能直接代表访存寻址开销（ALU vs AGU 两套机制）。

**方法**：在一块 64 字节对齐的内存中，让某个 qword 存储它自身的地址，rax 指向它。每种形式都访问**同一个地址**，cache 行为相同，区别只在寻址模式：

| 形式 | 指令 | 准备 |
| --- | --- | --- |
| base | `mov rax,[rax]` | `*p = p` |
| base+index | `mov rax,[rax+rcx]` | rcx = 0 |
| base+index×8 | `mov rax,[rax+rcx*8]` | rcx = 0 |
| base+小 disp | `mov rax,[rax+8]` | `*(p+8) = p` |
| base+大 disp | `mov rax,[rax+4096]` | `*(p+4096) = p` |
| base+index+disp | `mov rax,[rax+rcx+8]` | rcx = 0，`*(p+8) = p` |

**注意**：

- 用 disp 的形式时，被访问的地址变成 p+disp，需在该位置存入 p，保证链能闭合。
- 所有被访问地址都应在 L1 中且不跨 cache line；跑前先预热。
- 可选扩展：store 吞吐，`mov [rdi],rax` vs `mov [rdi+rcx],rax`（多组独立 store），检验 Haswell–Skylake 的 port 7 只支持简单寻址。

**输出**：与实验 1 并排的柱状图：同一寻址形式下 LEA 延迟 vs load-use 延迟，突出两者差异模式不同。

## Alternate hypotheses 与控制变量

观察到的时间差可能并非来自寻址形式本身，下列每一项都要有对应的排除手段：

| 替代解释 | 排除方法 |
| --- | --- |
| 频率变化（turbo、降频） | 用 core cycles 计量；检查 cycles ÷ 运行时间是否稳定 |
| 前端/解码瓶颈（长编码取指慢） | 实验 3 组 A、B 只改编码长度；延迟链 1–3 cycles 一条时前端通常不是瓶颈 |
| 循环开销 | 展开 200 条，减去空循环基线 |
| 测量噪声 | 每个 kernel 7 次取中位数，报告 min/max |
| P-core / E-core 混杂 | `taskset` 绑定单一核心类型，两类分开报告 |
| LEA 结论不能推广到访存 | 实验 4 直接测 load-use 延迟对照 |
| Cache/对齐效应（实验 4） | 访问地址相同、预热、64B 对齐、不跨 cache line |
| 微架构差异 | 记录 CPU 型号；若能访问另一台机器（Intel 与 AMD），重复实验 1 |
