x86 addressing-mode timing · microbenchmark study · Oct 2026

Adding zero to an lea can double its latency

Functionally identical x86 instructions that differ only in how the address is encoded can take different time. On the Intel Core Ultra 9 285H, the Efficiency cores take 2 cycles for any LEA that has both an index register and a displacement, even when both are zero. The Performance core on the same chip takes 1.

The headline result

Four ways to compute rax

Every instruction below produces exactly the value in rax: rcx is set to 0 and every displacement is 0. The only difference is which address parts are present in the encoding. Each LEA feeds the next one, so the time per instruction is its latency.

On the E-cores, an LEA is slow exactly when it has an index and a displacement. The number of parts doesn't matter, and the values don't matter.

Same value, different bytes

What actually changes in the instruction

An x86 address is base + index × scale + displacement. The base and index are registers; the displacement is a constant stored in the instruction's own bytes. An assembler silently drops a +0, so every encoding here was written byte by byte and checked with objdump. Writing rax*1 is how you put rax in the index slot instead of the base slot: mathematically a no-op, but a different instruction.

REX.W selects 64-bit operands, 8D is the LEA opcode, ModRM says which address form follows, SIB holds scale, index and base. Highlighted bytes are the displacement.

Why the cores differ hypothesis

A model that fits every measurement

Intel doesn't document its address adders, so this is an inferred model. It is consistent with all our data, but timing alone can't prove it.

E-core: a 2-input adder

A ← baseB ← index or disp
↓
A + B in one cycle

The index and the displacement compete for the same input. Any form that needs both takes a second step.

P-core: a 3-input adder

baseindexdisp
↓ missing parts fed in as 0
3-to-2 compress, then add, in one cycle

Every form takes 1 cycle, paid for with an extra logic layer on all six integer units: more area, more power, tighter timing.

The trade-off. Intel fits about four E-cores in the area of one P-core. The P-core spends area and power so that even rare address forms run at full speed. The E-core keeps the common forms ([base], [base+disp], [base+index]) fast and lets the rare ones take a second pass. The P-core pays elsewhere: a real scale factor (×2, ×4, ×8) costs it a cycle, consistent with a shift stage in front of its 3-input adder.

Still open: is the E-core's second step a second micro-op, or one micro-op that takes 2 cycles? The two E-core designs may even differ: Skymont's throughput drops about 2.2× (close to "two micro-ops on 8 units"), Crestmont's drops 4× (closer to "one unit can do it"). Windows' TotalIssues counter could settle it, but needs an admin run.

Method

How we measured

  • Dependency chains. Each LEA's output is the next one's input, so time per instruction is latency. 200 instructions unrolled per loop, 200,000 iterations, 7 repetitions, median reported.
  • Throughput. 8 independent chains with fixed sources, so instructions can overlap.
  • Core pinning. SetThreadAffinityMask to one logical CPU; core type from GetSystemCpuSetInformation EfficiencyClass and clock speed.
  • Cycles. rdtsc, divided by an add rax,rcx chain (1 cycle) timed just before and after each kernel, so frequency changes cancel out.
  • Sanity checks. imul chain = 3 / 4 / 5 cycles on P / E / LP-E; empty loop 0.005 cycles per instruction.

A trap in the original plan

The plan said to calibrate with an add rax,1 chain, assumed to take 1 cycle. On this CPU it takes 0.17 cycles on the P-core and 0.24 on the E-core: newer cores fold immediate adds before they reach an execution unit. Used as the reference, it made imul look like 16.5 cycles. The imul sanity check caught it, and the reference became add rax,rcx.

The wider survey

Every addressing form we measured

Before narrowing to the zero displacement, we ran the four planned experiments on all three core types. Every LEA latency and throughput matches uops.info within noise (black ticks in the figures).

Limits

What this study can't show

  • Cycles are calibrated from rdtsc, not read from a core-cycle counter. Windows has one, but it needs admin rights.
  • No per-port or per-micro-op counters on Windows (they need VTune or native Linux), so the adder model is inferred from timing.
  • The LP E-core being Crestmont is inferred from its match with uops.info's Meteor Lake-E rows.
  • The laptop ran on battery in the Balanced power plan; calibration cancels most frequency change.

AI use

  • The AI-drafted plan carried two outdated rules: add rax,1 as a 1-cycle reference, and Skylake's "3-part LEA is slow". Both failed on this CPU and were caught by sanity checks and uops.info.
  • Our first explanation, "three address parts are slow", was also wrong. Testing every base / index / displacement combination showed [rax*1+0], with only two parts, is slow too.
  • Harness bugs along the way: long is 32-bit on Windows (the codegen test emitted lea eax), and a missing _WIN32_WINNT hid the CPU-set API.
Reproduce

Run it yourself

From Desktop\LEA\harness on Windows, with WinLibs gcc and Python 3.12. The full suite takes about 2 minutes; the zero-displacement sweep about 5 minutes on six CPUs.

python run_all.py                                      # all experiments on CPUs 0, 2, 14 → results/results.csv
python run_all.py --only=ez --out=zero_disp.csv 0:P 10:P 2:E 6:E 14:LP-E 15:LP-E
python plot.py                                         # figures → results/*.png
bench.exe list                                         # logical CPUs with core type
